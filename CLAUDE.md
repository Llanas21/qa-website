# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Web system for Querify Analytics, a solo-operated data analytics academy (Excel, SQL Server, Power BI, Python — live courses over Microsoft Teams, Mexico market).

**The public site is conversion-only (since 13 oct 2026).** Every CTA pushes straight to "Apartar mi lugar" (the paid enrollment flow); the only lower-commitment option is a direct WhatsApp link (`https://wa.me/528443472957`), handled manually by the owner. The original lead-capture form + automated follow-up sequence was removed from the site on 13 oct and **deleted from the backend entirely on 29 oct 2026** (table `prospectos`, `POST /api/leads`, the hourly sequence, the WhatsApp inbound webhook, the Excel/SharePoint lead log, the admin prospect pages and the bienvenida/recordatorio/valor/cierre templates). Don't resurrect any of it without checking with the owner first; it was a deliberate removal.

Two independent parts in one repo:

```
querify-web/          Static public site (HTML/CSS/JS, zero dependencies, zero build step)
querify-backend/       Node.js (Express + PostgreSQL) API, admin panel, payments, certificates, calendar
ESTADO.md              Living project-status doc — read this first when resuming work
```

`ESTADO.md` (Spanish) is the actual source of truth for project state, decisions already made, and what's pending for production. Read it before making architecture-level suggestions.

## Commands

All commands run from `querify-backend/` (the site has no build step or package.json — it's served as static files).

```bash
npm install       # install deps
npm start         # run the server (node src/server.js)
npm run dev       # run with --watch (auto-restart on file change)
npm run db:init   # (re)initialize DB schema + seed via scripts/db-init.js
npm run hash -- "some-password"   # generate a bcrypt hash for ADMIN_PASS_HASH
```

There is no test suite, linter, or build step in this repo — do not invent npm scripts for these.

Local setup needs Node 18+ and PostgreSQL reachable via `DATABASE_URL` (see `.env.example`, copy to `.env`). With `STATIC_DIR=../querify-web` set, the backend serves the static site, the API, and the admin panel all from one process on `http://localhost:3000` (admin at `/admin`).

The backend runs in **simulation mode** per-integration: any of WhatsApp, email (Microsoft Graph), Outlook calendar, or Stripe that's missing credentials in `.env` silently simulates instead of failing — this lets the full inscripción → pago 1 → alumno → plan de pagos flow be exercised locally with zero external accounts. `config.simulate.{whatsapp,email,calendario,stripe}` in `src/db.js` is the source of truth for this behavior.


## Backend architecture (`querify-backend/src/`)

Request flow: `server.js` wires up Express, session middleware, the cron job, and (optionally) static file serving, then mounts `routes.js` at `/` and `admin.js` at `/admin`.

- **`db.js`** — the config module. All env vars are read once here into a single `config` object; every other module imports `config` from here rather than touching `process.env` directly. Also derives `config.simulate` (see above) and exports the pg `pool`/`query` helper.
- **`routes.js`** — public surface: `GET /api/cohortes/:curso` + `POST /api/inscripcion` (cohort selector and checkout kickoff for "apartar mi lugar"; validates server-side and checks a honeypot field), `GET /certificados/:token` (public, no login — streams an alumno's certificate PDF from Postgres; the token is random, not the alumno id, so links aren't guessable), and the Stripe webhook (`POST /webhook/stripe`, verifies the signature via `providers.verificarEventoStripe` on the **raw** body — `server.js` applies `express.raw()` to that one path before the global `express.json()`).
- **`engine.js`** — the business logic core: sending with the WhatsApp→email fallback (`enviarConVars`, always called with `canal: 'correo'` — see channel note), the inscripción/cohorte/pago logic (`iniciarInscripcion`, `confirmarInscripcion`, `confirmarPago`, `procesarWebhookStripe`, `revisarPagosPorVencer` — invoked hourly by the cron in `server.js`, for pagos 2-5), groups (`crearCohorte`/`actualizarCohorte`), transfers, and certificates (`subirCertificado` stores the PDF bytes + a fresh random token; `enviarCertificado` sends the `certificado` email through `enviarConVars`).
- **`certificados.js`** — renders the certificate PDF from an **HTML template**, `assets/certificado/plantilla.html` (designed by the owner; edit that file to change the design — it opens directly in a browser for preview, since signatures/logo/fonts sit next to it with relative paths). `generarCertificado({ nombre, curso })` replaces `{{NOMBRE_ALUMNO}}`/`{{NOMBRE_CURSO}}` (HTML-escaped), inlines images and fonts as data URIs, and prints to PDF with headless Chrome via `puppeteer-core`. On Railway (Linux) it uses `@sparticuz/chromium`; locally on Windows/macOS set `CHROME_PATH` in `.env` to the installed Chrome. Gotchas, all found by testing in a Debian container — **re-test there (`node:20-bookworm-slim` + `libnss3 libexpat1`) before deploying any change to this module or its dependencies**: (1) `@sparticuz/chromium` needs `libnss3` and `libexpat1`, declared in `railpack.json` at the repo root (keep the leading `"..."` in that list — without it the list replaces Railpack's own default packages instead of adding to them); (2) outside AWS Lambda it doesn't set `FONTCONFIG_PATH`, and without it Chrome loads **no** fonts and the PDF comes out with no text — `certificados.js` sets it; (3) `puppeteer-core`/`@sparticuz/chromium` are pinned to exact matching versions (23.10.4 / 131.0.1) — production on Railway runs **Node 18** (picked from `engines: >=18`), and newer versions of both need Node 22+. Fonts are bundled locally (`assets/certificado/fuentes/`, OFL) instead of Google Fonts, and generation throws if any font fails to load rather than sending a certificate with fallback text.
- **`calendario.js`** (28 oct 2026) — Outlook calendar reminders per group. One list of reminders for all courses (table `recordatorios`, edited at `/admin/recordatorios`, seeded from the owner's process draft: 28-day pre-course planning, 2 days before, first/last day, certificates); each becomes an event per group × mailbox in `CALENDARIO_BUZONES` (José and David), titled with the group code `CURSO-DIAS-MMYY` (`codigoGrupo`, e.g. `EXCEL-SAB-1026`). Days count from the `ancla` (`inicio` = first class, negatives = before; `fin` = last class). One-day reminders are timed events at `CALENDARIO_HORA` (10:00) with the alert at that time; ranges (`dia_hasta`) are all-day multi-day events with the alert at 10:00 the day before (Outlook counts all-day alerts from midnight — the owner picked this). Each reminder has an `alcance`: `grupo` (one event per group) or `general` (one shared event per reminder × date when several groups fall on the same day, titled "Grupos del 31 oct · …", stored in `eventos_generales` and recomputed from all dated groups on every sync) — the 28-day promo planning is general, the rest per group (29 oct 2026). Past ones are created too, on purpose (owner wants to see what should already be done when a group is registered late). Any change marks `cohortes.calendario_pendiente`; `sincronizarPendientes()` (on save, on boot, and in the hourly cron) creates/moves/deletes events via `cohorte_eventos` (stores each Graph event id + a hash to skip unchanged PATCHes), serialized in one queue to avoid duplicates, aborting the run on 401/403. Needs Graph application permission `Calendars.ReadWrite`; without `CALENDARIO_BUZONES` it does nothing, without Graph credentials it simulates.
- **`providers.js`** — the only place that talks to external services: Meta Cloud API for WhatsApp (template sends only, unused in practice), Microsoft Graph for email and the Outlook calendar, and Stripe (Checkout Sessions, customers/CLABE, webhook signature verification). Email is sent via `POST /users/{buzón}/sendMail` as a shared mailbox (`MAIL_FROM`); there is no SMTP — email and calendar share one Graph app registration/token (`getGraphToken`, `GRAPH_TENANT_ID`/`GRAPH_CLIENT_ID`/`GRAPH_CLIENT_SECRET`). Every function here degrades to simulation when `config.simulate.*` is true.
- **`templates.js`** — the email templates (pago/inscripcion/certificado/transferencia), each in three forms: `render()` (plain text — what's logged to `mensajes.contenido` for the alumno's history), `renderHtml()` (the actual branded HTML email a recipient receives — logo header + card layout + CTA button, all inline styles since `<style>` in `<head>` isn't reliable across mail clients), and Meta template params (for WhatsApp — unused in practice, kept intact). `fill()` supports any `{{N}}` placeholder so the `pago` template can carry monto + liga de pago. For HTML buttons, use `<a style="display:inline-block">` wrapped in a `<div style="text-align">`, not a `<table align="center">` — modern mail clients (Gmail, Apple Mail) ignore the deprecated `align` attribute, even though it renders centered in a plain browser/Puppeteer preview.
- **`admin.js`** — self-contained server-rendered admin panel (session-based login, no separate frontend framework — HTML is built with template literals and a shared `layout()` helper in this same file). Mobile-first, installable as a PWA (`GET /admin/manifest.webmanifest`, `start_url: /admin/alumnos`). Nav (hamburger side-drawer): **"Grupos"** (`/admin/alumnos` — the label changed 15 oct 2026 but the route didn't; lists cohortes with ≥1 alumno, newest first; a group opens `/admin/grupo/:id` with its alumnos and a FAB for manual alta), **"Pagos"** (`/admin/pagos`, cross-alumno ledger with a FAB to register a manual payment), **"Cohortes"** (edit fecha de inicio/último día/días/cupo, create new ones; each card links to its `/admin/grupo/:id` even with zero alumnos), **"Recordatorios"** (the calendar reminder list, see `calendario.js`), **"Errores"** (failed sends). `/admin` redirects to Grupos. `/admin/alumno/:id` has the 5-payment plan (+ "Liquidar"), "Dar de baja", and the "Enviar certificado" button (`certificados.generarCertificado` → `engine.subirCertificado` → `engine.enviarCertificado` in one request).

### Data model (`db/schema.sql`)

Tables: `mensajes` (append-only history of every email sent/failed/simulated and internal note, per alumno via `alumno_id`), `cohortes` (curso × modalidad × `dias` × fecha_inicio — `dias` is `LM`/`MJ` entre semana or `SAB`, unique together so two weekday groups of one course can share a start date; `fecha_fin` defaults to 10 weeks (`calendario.fechaFinPorDefecto`) but is editable for holidays; with `cupo_maximo`/`lugares_ocupados` — replaces the old `fechas_inicio`; can have several rows per curso×modalidad over time, one per generation, unlike the old table which held only "the next" date), `alumnos` (created only when payment 1 is confirmed; also holds the latest generated certificate — `certificado_pdf` BYTEA, stored in Postgres because Railway's container filesystem is wiped on every deploy — plus `certificado_nombre`/`certificado_token`/`certificado_subido_en`), `pagos` (5 rows per alumno, semanas 0/2/4/6/8, `estado` pendiente/pagado/vencido/cancelado — cancelado only via baja, `metodo` stripe/transferencia/manual), plus `recordatorios`, `cohorte_eventos` and `eventos_generales` for the calendar (see `calendario.js`).

Schema is applied idempotently on every boot (`initDb()` in `server.js` runs `schema.sql` via `CREATE TABLE IF NOT EXISTS`, then seeds `cohortes` only if empty) — there is no separate migration tool or migration files. Inline `ALTER TABLE ... ADD/DROP COLUMN IF EXISTS` statements in `schema.sql` cover column-level changes. **`schema.sql` also runs in production on every deploy**, so any destructive statement there (like the `DROP TABLE IF EXISTS prospectos` of 29 oct 2026) executes against real data as soon as it ships.

### Business rules that are load-bearing (don't casually change without checking `ESTADO.md`)

- **Channel logic (changed 1 oct 2026 — see `ESTADO.md`): the site is email-only now.** The real WhatsApp number was migrated off the Cloud API to the regular WhatsApp Business app, so no number is connected anymore. Every `enviarConVars()` call site hardcodes `canal: 'correo'` regardless of whether a phone number is on file — the WhatsApp→email fallback machinery in `enviarConVars`/`providers.js` is left intact (unused, not deleted) in case a number is ever reconnected. The phone field is still captured on the inscripción form, but purely as reference info the operator can see in `/admin` — it's never used to send anything. Don't revert this without checking `ESTADO.md` first.
- **Baja (`alumnos.fecha_baja`, 20 oct 2026)** — "Dar de baja" in `/admin/alumno/:id` (`engine.darDeBaja`) for students who quit: frees their cupo spot, sets their pending/vencido pagos to `estado = 'cancelado'`, hides the certificate button, tags them "baja" in their group; nothing is deleted. It **replaced the "Archivar"/"Reactivar" buttons**. `alumnos.archivado` still exists and `revisarPagosPorVencer` still skips archived alumnos — kept only for the alumnos already archived as the 1 oct 2026 historical batch — but nothing in the panel sets it anymore.
- **Manual alta** (`engine.altaAlumnoManual`): rejects cohortes with no `fecha_inicio` (the payment plan is computed from it — without the check, `new Date(null)` produced 1970 due dates and a burst of reminder emails, which happened once in production). The "Enviar correo de bienvenida" checkbox (on by default) controls whether the `inscripcion` email goes out. `revisarPagosPorVencer` never auto-reminds a pago whose due date was already before the alumno's `fecha_alta`, so registering someone into a group that's already halfway through doesn't spam them about payments they likely made; those show as vencido in the panel to be marked paid by hand. Normal Stripe enrollments are unaffected (the site only offers cohortes that haven't started).
- **Changing a group's start date (`engine.actualizarCohorte`)** shifts its `fecha_fin` by the same amount (unless edited at the same time), recalculates the due dates of its alumnos' unpaid pagos (`recalcularPagosCohorte`, same `SEMANAS_PAGO` offsets; paid ones untouched) and moves its calendar events. Before 28 oct 2026 the date edit did none of this.
- **Cupo se ocupa al confirmar el pago 1, no al iniciar el checkout** — `iniciarInscripcion` only checks capacity to avoid handing out a dead link; `confirmarInscripcion` (called from the Stripe webhook) is what actually increments `lugares_ocupados`, creates the `alumno`, and generates the 5 `pagos` rows.
- **Pagos 2-5 se cobran por WhatsApp/correo, no con tarjeta guardada** — no recurring/saved-card billing; the cron (`revisarPagosPorVencer`) generates a fresh Checkout Session per payment near its due date and emails it.
- **SPEI bank transfer via Stripe (23 oct 2026)** — every Checkout Session (inscripción and pagos 2-5) is created with a Stripe `customer` and offers `card` + `customer_balance` (`mx_bank_transfer`). Each alumno has one Customer (reused by email, `providers.clienteStripe`) = one **permanent CLABE of their own**, stored in `alumnos.stripe_customer_id`/`clabe`/`clabe_banco`/`clabe_titular`. Webhook flow: `checkout.session.completed` with `payment_status: 'unpaid'` = student chose transfer → `engine.enviarDatosTransferencia` emails the `transferencia` template; `checkout.session.async_payment_succeeded` = money arrived → same confirm path as card, `metodo = 'transferencia'`; `customer_cash_balance_transaction.created` (`funded`) = a transfer straight to their CLABE → `engine.procesarTransferencia` applies the cash balance to pending pagos in order (skips if a transfer PaymentIntent is open — Stripe reconciles that one itself; leftovers stay as saldo a favor). Load-bearing: an **open transfer PaymentIntent swallows the customer's next transfer**, so `confirmarPago` cancels open ones for that same pago and `iniciarInscripcion` cancels the customer's open inscripción ones; `cobrarDeSaldo` cancels its PI if it didn't succeed. When the student picks transfer, Stripe shows its own hosted instructions page and never redirects to `success_url`. Local testing: `stripe listen --forward-to localhost:3000/webhook/stripe` + `stripe.testHelpers.customers.fundCashBalance`, or the test-key-only "Simular transferencia" button in `/admin/alumno/:id`.
- **Business decisions already settled** (see `ESTADO.md` § "Decisiones ya tomadas" for the full list and reasoning) — WhatsApp via Meta Cloud API directly (no third-party provider), Node/Express over the originally-considered Python/FastAPI, Railway over Render for hosting (Render's free tier sleeps, breaking the hourly cron), Instagram DM stays manual/unautomated, Stripe Checkout Sessions (not Payment Links) for the enrollment flow, `cohortes` merged into (replacing) `fechas_inicio`. Don't reopen these without a concrete new reason.

## Frontend (`querify-web/`)

Static HTML/CSS/JS, no framework, no bundler, no npm — edit files directly and open/serve them as-is.

- **`assets/css/styles.css`** — all design tokens (colors, fonts, radii, shadows) live in a single `:root` block at the top. Change the palette/typography only there. Light theme, primary blue `#3B82F6`/`#2563EB`, deliberately no glow effects or heavy shadows; fonts are Montserrat (headings), Work Sans (body), IBM Plex Mono (code-like details).
- **`assets/img/querify-logo-completo.png`** — the owner's full logo (wordmark "Querify Analytics / ACADEMY" + the Q, transparent PNG, margins cropped), used since 30 oct 2026 as the single `<img class="logo">` in every page's header/footer `.brand` block — it replaced the old icon + HTML text wordmark. Swap this one file to change it everywhere.
- **`assets/img/querify-logo.png`** — the Q mark alone (transparent PNG), still used where a square icon is needed: favicon (`<link rel="icon">`) and the admin PWA manifest. The full logo is also in the admin topbar/drawer/login and in email headers (`templates.js` `LOGO`, absolute URL to the live site — so a new logo file must be deployed before emails can show it).
- **`assets/img/querify-logo-apple-touch-icon.png`** — same logo flattened onto an opaque white background (no alpha channel), added 15 oct 2026 specifically for `<link rel="apple-touch-icon">` in the admin panel (`admin.js`). iOS doesn't support transparency in home-screen icons — it fills transparent pixels with black — so this one exists only to avoid that; the regular transparent PNG is still correct everywhere else (favicon, manifest). Regenerate it (flatten onto white, no alpha) if the logo ever changes.
- **`assets/js/app.js`** — mobile nav toggle, dynamic footer year, and the inscripción (apartar lugar) form (`initInscripcionForm`, on `cursos/inscripcion.html`) — it awaits `POST /api/inscripcion` and redirects to the real Stripe Checkout URL (or shows the error, e.g. "sin cupo") because there's a real payment step to hand off to. There used to also be a lead-capture form (`initLeadForm`); it was removed 13 oct 2026 (see the note at the top of this file). `PHONE_LEN` (digit-count validation per country code) survives because the inscripción form's WhatsApp field still uses it, even though that field is optional/informational now.
- To point the site at a backend hosted separately (not same-origin), change `COHORTES_ENDPOINT`/`INSCRIPCION_ENDPOINT` in `app.js` to the full backend URL and add the site's origin to `CORS_ORIGINS` in the backend's `.env`.
- `cursos/*.html` are the 4 course landing pages, each with real course curriculum content (not placeholder), plus `cursos/inscripcion.html` — one shared page (not per-course) for "apartar mi lugar": cohort/date picker with live cupo (from `GET /api/cohortes/:curso`), the 5-payment plan, and the form that kicks off Stripe Checkout. `inscripcion-gracias.html` (repo root) is the post-payment confirmation page.
